# P0.12 / #612 — opt-in HTTPS transport candidate (DRAFT, NOT SECURITY-APPROVED)

**Release status:** v3.0.5 last published; v3.1.0 UNRELEASED, publication_authorized=false. This implementation is a proposed *real* HTTPS client under independent security review. It is not production-ready, has not been exercised against Internet targets, and does not certify end-to-end SSRF resistance.

## Boundary and explicit activation

Normal invocation and the Static CI registration execute only local fixtures. No DNS, socket, SSL handshake or HTTP traffic may occur unless the operator explicitly passes **all** of --network-opt-in, one or more exact --host values, one or more --url values and an absolute --journal output path. The selected URLs must occur byte-for-byte in the Markdown external-link inventory **recomputed from immutable Git tree/blob objects at the pinned HEAD, not the working tree**, with Git object replacement explicitly disabled (`--no-replace-objects`) and automatic promisor-object fetching disabled (`GIT_NO_LAZY_FETCH=1`) for **every** identity-establishing Git read. A partial clone missing required blobs must fail instead of contacting an unapproved Git remote. This prevents both skip-worktree/assume-unchanged mutations and `refs/replace` blob substitution from being falsely attributed to the original commit. Git object reads also run with a scratch HOME/XDG configuration directory, an explicitly empty system/global Git configuration, a POSIX system-default PATH, inherited Git object/config variables stripped, protocol-from-user disabled and core.fsmonitor=false. These measures constrain parent-side inherited Git environment; repository-local Git config and a compromised local UID remain outside a cryptographic trust boundary. The parent passes the exact checkout SHA and inventory fingerprint to each isolated worker; the worker recomputes the trusted inventory and refuses to access the network if either value differs. The parent also rejects child output with different source identifiers. The operator does not supply a trusted inventory SHA or fingerprint; the tool recomputes them. The journal is a newly created private file; it cannot overwrite an existing report. Use an output directory **outside the repository**, to prevent untracked output from invalidating a clean-checkout verification in the child worker.

Example command for a reviewed, egress-controlled environment only (illustrative, DO NOT run during normal CI):

    python3 tests/checks/repository/p012_opt_in_https_probe.py --network-opt-in --host example.org --url https://example.org/path-from-current-inventory --journal /tmp/abntexto-p012-real.jsonl --timeout 8

The hostname and URL are illustrations, not a claim that this URL exists in this repository's inventory.

### Internal worker journal admission (#620)

The internal `--_worker` CLI mode is **not an operator entry point**. Under POSIX it now requires a private anonymous pipe descriptor explicitly inherited by the child with `pass_fds`. The parent creates this pipe **only after opening the exclusive REAL_HTTP journal and fsyncing its start record**. It transmits a bounded request capability identifying the exact URL, allowed host tuple, checkout SHA, inventory fingerprint, **the immutable SHA-256 of the first (start) journal record** and parent PID. The changing `journal.previous` is used only to chain subsequent result/finish records; all selected workers receive the same stored `journal.start_sha256` independent of selection order. The worker verifies the pipe type, request binding, and the **actual private REAL_HTTP journal start record on disk** (owner, permissions, one regular-file link, SHA-256 of record bytes, internal checksum, schema, source identity and selected URL) **before** recomputing the inventory or issuing DNS/TLS/HTTP. An arbitrary 64-character checksum alone is insufficient. Direct `--_worker` calls without the inherited descriptor fail closed; the parent uses bounded nonblocking IPC writes and retains responsibility for the child's lifecycle. Normal `--network-opt-in` entry still requires the parent-owned absolute journal path.

The trust model treats the local operating-system user running this tool and its installed Python/Git source as trusted; the remote DNS/TLS/HTTP endpoints and input URLs remain untrusted. This is a process-lifecycle and on-disk evidence consistency control, **not a cryptographic proof against hostile code running as the same OS user**. A sufficiently privileged local process could deliberately create a forged pipe or modify the Python source. Do not claim this authenticates a remote requester or replaces system egress filtering. The current transport requires POSIX process supervision; on non-POSIX systems the live parent-worker operation fails closed until equivalent guarantees are independently reviewed. The Static suite includes an offline direct-worker rejection and parent-capability positive/negative fixtures.

## Exact network construction

- The worker checks every DNS answer with the merged public-IP policy. A single private, reserved or scoped answer rejects the entire response. The worker chooses one numeric global IP and never passes a DNS hostname into the TCP connect operation.
- Direct TCP socket to numeric IP on port 443, then compare actual getpeername() with the pinned address. Python's verified default CA-backed SSL context handshakes using the original approved hostname as TLS SNI and certificate-validation hostname. The certificate must exist, and the post-handshake peer IP must still equal the selected address.
- HTTP/1.1 HEAD request uses the original hostname in Host and only a validated path/query. No urllib, requests, proxies, custom CA environment or redirects inherited from a higher-level client. A single pinned-IP GET with Range: bytes=0-0 is used only if HEAD returns 405/501.
- The parser stops at the **first** CRLF-CRLF of each HTTP response block, follows bounded 100/102/103 informational blocks to their final status, rejects unsupported 101 upgrades, and applies **one aggregate limit of 8 KiB to all headers** and **zero application-level body bytes**. Thus an arbitrary server body, or a server ignoring Range, cannot trigger unbounded downloading. Redirect bodies are never consumed. A redirect is allowed only to an approved HTTPS host, with a new DNS vetting and IP pinning on the next hop, no more than three redirects.
- A separate process per URL has a *single monotonic network deadline* encompassing DNS, connect, TLS, HEAD, GET fallback and redirects; a separate bounded one-second cleanup grace applies after the process group is signaled. The POSIX parent blocks **both SIGTERM and SIGINT** with `pthread_sigmask` before spawning the child, restores delivery only inside a guarding `try/finally`, and masks both signals during `killpg`/wait cleanup; the child explicitly unmasks both on startup. **Signal handlers only record a shared cancellation request; they never raise asynchronous Python exceptions.** The POSIX parent checks that state while using selector reads and a non-reaping `waitid(WNOWAIT)` loop (at most 100 ms per selector interval) and propagates cancellation synchronously **only after** terminating the entire POSIX process group and reaping its direct worker child. **The group is always sent SIGKILL, even when the worker leader has already exited**: descendants can retain a stdout pipe and continue running after the leader has exited with status 0. To prevent PID/PGID reuse from causing SIGKILL to reach an unrelated process, **the POSIX supervisor never calls Popen.communicate(), poll(), or wait() before killpg()**. It reads stdout with a selector and checks exit state through `waitid(WNOWAIT)`, keeping the exited leader unreaped as a PID/PGID identity anchor. The leader is reaped with **a bounded `wait(timeout=1.0)`** **only after** group termination. If this cleanup cannot be confirmed, the operation fails closed and the REAL_HTTP journal remains PARTIAL; it does not claim an absolute kernel-level termination bound. Linux/compatible POSIX systems without non-reaping wait inspection fail closed. **POSIX execution rejects any non-default SIGCHLD handler before spawning**, because ignored/custom child signal handling can invalidate the PID/PGID anchor. A pre-kill `waitid(WNOWAIT)` probe refuses to signal a worker that was unexpectedly reaped externally. The dedicated CLI has a default SIGCHLD disposition; externally embedded Python reapers and inherited sigaction flags outside this assumption require separate assessment. The offline self-test verifies this refusal without creating a child. Its emergency cleanup re-signals a group only while the direct leader remains an unreaped child verified through `waitid(WNOWAIT)`; it never sends `killpg` a second time after the leader has already been reaped. Offline regressions cover both a fast-exiting leader without descendants (prove its PID remains unreaped at `killpg`) and a leader that backgrounds a continuously writing descendant (prove writing ceases after timeout). Descendants cannot be directly `wait()`-reaped by a non-parent, so their eventual zombie reaping remains the responsibility of the system init/subreaper. Therefore even the *first* SIGTERM or SIGINT delivered after a normal timeout entered `finally`, but before signal masking, cannot abort `killpg()`/`wait()`. The same rule covers mixed SIGTERM→SIGINT and SIGINT→SIGTERM sequences. Offline tests inject SIGTERM and SIGINT during `Popen`, the simulated nonreaping read, and the first cleanup instruction, separately and in alternating order; every path must kill and reap the child. SIGKILL of the parent, non-POSIX descendant cleanup and live egress security still require independent review. Runtime disables environment inheritance for the child, closes other descriptors, uses isolated Python mode and a fixed worker entry point; the runner invokes no shell.
- Per-URL status is persisted immediately to a private REAL_HTTP schema-2 JSONL journal with per-record checksum, SHA-chain and fsync. On POSIX the containing directory is fsynced after creation. Missing finish means PARTIAL; this is not a signature or authentication against a malicious writer. Failures of one URL should not discard earlier receipts. Windows child-process descendant termination and directory-entry crash durability are not certified.

## Known hard limits / independent-review requirements

- **This is not an audited SSRF defense.** Local network egress filtering is a separate mandatory control; future adversarial validation must use a disposable egress-restricted environment and an independent reviewer for the exact final SHA.
- DNS rebinding and mixed public/private records, IPv6/mapped addresses, certificate/SNI correctness, proxies, slow DNS, handshake/header trickle, malformed redirect, HEAD-to-GET behavior, HTTP parsing, interruption, process cleanup and partial journal recovery must undergo negative tests and controlled real integration. The fake tests and static approval alone are insufficient.
- The worker currently selects the first supported approved IP, without fallback to other public A/AAAA addresses. This may yield false-negative NETWORK_ERROR; do not report this as an absent document.
- A HEAD-supported server may misbehave and report statuses different from GET; record classifications conservatively. HTTP 401/403 is ACCESS_RESTRICTED, not broken. Timeout and network errors are not evidence of missing links. No 2xx GET body is retained.
- There is no real-network check in default CI, in module import or in the self-test. A child receives no inherited HTTP_PROXY, HTTPS_PROXY, SSL_CERT_FILE, PYTHONPATH, or HOME.
- Production readiness also requires review of live REAL_HTTP journal validation and source fingerprint binding, process-tree portability, parser interoperability, and an independent red-team-style security gate. The PR must remain DRAFT and **MUST NOT MERGE** until all applicable gates are completed and the independent reviewer explicitly signs off.
