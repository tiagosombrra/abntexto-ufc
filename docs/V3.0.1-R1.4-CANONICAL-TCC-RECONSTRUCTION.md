## Trigger

Maintainer inspection of the canonical PDF after PR #305 merge showed that the document did not visibly contain the depth of changes requested for the canonical TCC.

This finding reopens source acceptance. It is not explained by a stale PDF: R2 was built after the R1.3 source accepted by the repository.

## Root cause

R1.1 normalized source filenames but intentionally did not change rendered content.

R1.3 was explicitly implemented as an **additive, bounded rewrite**. From the R1.2 control point `3ad68d22eb7e2842679437dde3b0b25755179f7e` to the accepted R1.3 source `704cedaa9960b87ae6035ac08fa4cc4c286ea9aa`, canonical source changes were only 202 additions / 27 deletions across `template/main.tex` plus the seven textual files, and `6-academic-objects.tex` was left unchanged.

More importantly, the R1.2 coverage matrix was never reconciled before R1 was declared DONE. On the merged main it still contains:

- 4 `MISSING`;
- 18 `PARTIAL`;
- 11 `DOCUMENTED_NEEDS_TRACE`;
- 18 `COMPLETE_MAPPED`;
- 2 `SEPARATE_PROFILE`.

R1.2's own completion rule said unresolved release-required topics had to be reconciled before closure. R1.3 evidence claimed those gaps were closed even though the matrix still said otherwise. The acceptance interpretation was therefore wrong.

The seven sequential source files currently render their highest textual level using `\section{...}`. Renaming files to `1-...` through `7-...` did not create a visible structural change. R1.4 must verify the correct primary structural command for the class/normative model and validate the rendered hierarchy/TOC rather than assuming filenames satisfy the requested organization.

## Corrected canonical contract

The canonical reference rooted at `template/main.tex` must be a **complete pedagogical TCC-shaped document**, not the prior guide with a small number of explanatory callouts.

For every release-required topic, the final PDF/source pair must show:

1. authority classification: ABNT normative, UFC institutional, project policy, or example/recommendation;
2. the practical rule or expectation;
3. the expected visible result;
4. the exact public `abntexto-ufc` key, command, environment or source-file mechanism;
5. a concrete compilable/rendered example when applicable;
6. the repository test/validator evidence that protects the behavior.

Project policy must never be presented as universal ABNT/UFC authority. Web/Lite must never claim Deep-only proof. Accessibility claims must remain bounded by actual evidence.
