R5 is intentionally a dynamic transport state. Every session resolves current Git/PR/workflow facts first and follows the applicable branch below.

## Single candidate marker

The only R5 marker is:

`release/v3-release-candidate.json`

## No self-invalidating receipt commit

After Stage C exact-main certification succeeds, do **not** commit a source/documentation receipt merely to write the exact SHA or artifact hashes: that would create a new main SHA and invalidate R5.

Until tag/publication freezes the candidate, live exact-main receipts belong to immutable GitHub Actions runs/artifacts and issue #304. The tracked documents already contain this deterministic continuation procedure, so a new session can recover by resolving Git and the issue/run facts.

If a Stage C failure requires a source change, R5 is invalidated. Create/fix through an auditable branch/PR, update these controls there, and repeat Stage A → B → C.
