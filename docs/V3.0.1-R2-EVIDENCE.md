## Purpose

R2 makes the complete PDF rooted at `template/main.tex` a first-class release reference without creating a second PDF-generation path. The existing reproducibility gate remains authoritative; this lot adds exact-SHA provenance enforcement, a dedicated retained artifact and static CI protection around that wiring.

## Existing generator retained

`make release-check` already invokes `tests/integration/release-reference-reproducibility.sh`. That script performs two independent clean builds of the canonical source and writes:

- `artifacts/validation/release-reference-pdf.pdf`;
- `artifacts/validation/release-reference-reproducibility.json`.

It already checks byte-identical builds, font embedding, the portable PDF/CLI validation path, PDF/A-2b and Unicode text extraction. R2 intentionally does not duplicate this implementation.

## R2 implementation

The commit containing this document changes only release-artifact/orchestration/control surfaces; resolve its exact SHA dynamically from Git before using CI evidence.

### Linux Release Check

`.github/workflows/linux-release-check.yml` now performs a fail-closed provenance check immediately after `make release-check`. The gate requires:

- non-empty canonical PDF and present JSON evidence;
- evidence `status=PASS`;
- evidence `source_sha` exactly equal to the workflow `SOURCE_COMMIT_SHA`;
- `canonical_source=template/main.tex`;
- `canonical_output=artifacts/validation/release-reference-pdf.pdf`;
- exactly two independent clean builds with `identical_sha256=true`;
- SHA-256 of the retained PDF equal to both build records;
- `font_embedding=PASS`;
- `portable_pdf_validator=PASS`;
- `pdfa_2b=PASS`;
- `unicode_extraction=PASS`.

The successful workflow emits `CANONICAL-REFERENCE-EVIDENCE status=PASS ...` and uploads the PDF plus JSON together as:

`abntexto-ufc-v<version>-canonical-reference-<run_id>`

The generic `linux-release-validation-<run_id>` artifact remains available for broader diagnostics, but it is no longer the only way to discover the canonical reference PDF.

### CI scope control

`tests/integration_suites.py` classifies `.github/workflows/linux-release-check.yml` as orchestration. A synchronization containing only release-workflow/orchestration plus documentation therefore selects the ordinary PR `smoke` suite rather than another `complete` Linux integration. This does not reduce final certification: the same workflow change directly triggers Linux Release Check, and both `release/final-certification-candidate.json` and `release/v3-release-candidate.json` continue to force `complete`.

`tests/checks/linux_integration_suites.py` statically protects:

- the dedicated canonical artifact and both required paths;
- candidate-SHA provenance validation markers;
- the `smoke` classification for release-workflow-only changes;
- the rule that release-candidate markers dominate orchestration and force `complete`.
