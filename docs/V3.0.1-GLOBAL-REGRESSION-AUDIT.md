## Findings — pre-publication blockers

### G1 — Control-plane authority is internally contradictory

Severity: **BLOCKER BEFORE R6**.

The current `AGENTS.md` correctly prioritizes current Git and the v3.0.1 correction state. However, several tracked documents still look active while describing old recovery states:

- `docs/ARCHITECTURE.md` identifies its target as v3.0.0;
- `docs/HANDOFF-V3.0.0.md` still names `release/v3.0.1-recovery` and says exact-main recertification is pending;
- `docs/ROADMAP-V3.0.0.md` still says the recovery merge is in progress and R5 is blocked;
- `release/v3-roadmap.json` still contains the old recovery candidate state;
- `docs/CTAN-RELEASE.md` still shows R4/R5/R6 as pending;
- `docs/V3-RELEASE-READINESS.md`, `V3-RELEASE-RECOVERY.md` and `V3-RELEASE-PHASE-END.md` still present pre-merge/recovery-era current status;
- `docs/ENGINEERING-LANGUAGE.md` explicitly names the stale roadmap/handoff files as current phase/status authority.

This is not a PDF/runtime failure, but it is a release-governance defect: a fresh maintainer/chat can follow an obsolete control path even though newer documents exist.

### G2 — Repository contract protects stale control-plane files as current required surfaces

Severity: **BLOCKER BEFORE R6**.

`tests/checks/repository_contract.py` currently requires:

- `docs/ROADMAP-V3.0.0.md`;
- `docs/HANDOFF-V3.0.0.md`;
- `release/v3-roadmap.json`;

and explicitly exempts them from stale-content scanning.

That policy was useful during the v3 migration but now preserves the ambiguity identified in G1. The release should not be published while the permanent repository contract directs future maintenance toward superseded control-plane documents.

### G3 — Active technical version residue

Severity: **PRE-PUBLICATION FIX**.

`tools/fetch-reference-images.py` uses User-Agent `abntexto-ufc/3.0.0 reference-assets`. Change it to derive/use the canonical 3.0.1 identity or a version-neutral project User-Agent.

### G4 — Historical phase documents are not consistently labeled historical

Severity: **PRE-PUBLICATION GOVERNANCE FIX**.

Several otherwise useful evidence documents preserve phase-time statements that are now false as current state, for example old `item 33 = NORMATIVE-REVIEW`, “Scientific Article active”, or “Final Certification active”. Historical evidence must remain unchanged in substance, but every such file needs an unambiguous historical/superseded banner and pointer to the current 3.0.1 continuation authority.

Examples include `V3-CORRECTION-PLAN.md`, `V3-REGRESSION-AUDIT.md`, `V3-REFERENCE-PDF-VISUAL-REVIEW.md`, `V3-SCIENTIFIC-ARTICLE*.md`, and `R3-HARDENING-INVENTORY.md`.

### Consequence

Fixing G1–G4 changes the repository after the already-green exact-main candidate. Therefore the existing `ab641d49c5f6a79ff54a16a78d1946a6e008fe6d` must become **baseline evidence only**. After the governance/identity correction is merged, R5 complete exact-main certification must be rerun on the new SHA before R6.

This recertification cost is preferable to publishing a candidate whose own maintenance documents disagree about the active release state.
